# Git Convention

## 1. Commit Convention

### 1.1. 커밋 메시지 형식

`<작업 타입>: <작업 내용>`

- `feat: 회원가입 기능 구현`
- `fix: 로그인 시 토큰 만료 오류 수정`
- `docs: README 설치 방법 수정`

### 1.2. 작업 타입

| 작업 타입 | 작업 내용 |
| --- | --- |
| `begin` | 프로젝트 시작 |
| `feat` | 새로운 기능 추가 및 구현 |
| `docs` | 문서 파일 추가 및 수정 |
| `add` | 기존 기능에 코드 추가 및 코드 수정 |
| `typos` | 단순 오타 수정 |
| `fix` | 버그 및 에러 수정 |
| `test` | 테스트 코드 작성 및 수정 |
| `rename` | 파일 및 경로 이동, 이름 변경 |
| `refactor` | 코드 리팩토링 |
| `comment` | 주석 추가 및 변경 |
| `remove` | 파일 및 코드 삭제 |
| `branch` | 브랜치 추가, 병합 등 |
| `chore` | 빌드 업무 수정, 패키지 매니저 수정, 패키지 관리자 구성 등 |

### 1.3. 커밋 작성 규칙

1. 작업 타입은 위 표에 정의된 유형을 사용한다.
2. 작업 내용은 무엇을 변경했는지 명확하게 작성한다.
3. 커밋 하나에는 가급적 하나의 목적에 해당하는 작업만 포함한다.
4. 불필요한 수식어를 제외하고 간결하게 작성한다.
5. 단순 오타 수정은 `typos`, 버그 수정은 `fix`를 사용한다.
6. 새로운 기능을 구현한 경우 `feat`를 사용한다.
7. 문서 변경만 포함하는 경우 `docs`를 사용한다.
8. 기능 변경 없이 코드 구조만 개선하는 경우 `refactor`를 사용한다.

### 1.4. 커밋 메시지 예시

| 작업 유형 | 예시 |
| --- | --- |
| 프로젝트 시작 | `begin: React 프로젝트 초기 설정` |
| 기능 추가 | `feat: 회원가입 화면 구현` |
| 기존 기능 수정 | `add: 운동 기록 목록에 페이징 추가` |
| 버그 수정 | `fix: 웹캠 중복 시작 오류 수정` |
| 오타 수정 | `typos: 변수명 오타 수정` |
| 테스트 | `test: 회원가입 폼 테스트 코드 작성` |
| 문서 수정 | `docs: 아키텍처 문서 업데이트` |
| 리팩토링 | `refactor: 자세 분석 로직 훅으로 분리` |
| 파일 이름 변경 | `rename: 사용자 타입 파일명 변경` |
| 코드 삭제 | `remove: 사용하지 않는 유틸 함수 삭제` |
| 브랜치 작업 | `branch: develop 브랜치 병합` |
| 환경 설정 | `chore: 패키지 의존성 설정 변경` |

## 2. Branch Convention

### 2.1. 브랜치 구조

| 브랜치 | 역할 |
| --- | --- |
| `main` | 배포 가능한 안정 버전 관리 |
| `develop` | 개발 중인 기능을 통합하는 브랜치 |
| `feature/기능명` | 개별 기능을 개발하는 브랜치 |

### 2.2. 브랜치 생성 규칙

1. 기본 브랜치는 `main`, `develop`을 사용한다.
2. 새로운 기능은 `develop`에서 `feature/기능명` 브랜치를 생성하여 개발한다.
3. 기능 개발이 완료되면 `develop`을 대상으로 PR을 생성한다.
4. 기능명은 소문자를 사용한다.
5. 기능명이 여러 단어로 구성된 경우 하이픈(`-`)으로 구분한다.
6. 브랜치명은 기능의 목적을 명확하게 나타내도록 작성한다.

### 2.3. 브랜치명 예시

| 목적 | 브랜치명 |
| --- | --- |
| 회원가입 기능 | `feature/signup` |
| 로그인 기능 | `feature/login` |
| AI 에이전트 기능 | `feature/ai-agent` |
| 운동 자세 분석 | `feature/pose-analysis` |

### 2.4. 브랜치 작업 흐름

1. `develop` 브랜치에서 기능 브랜치를 생성한다.
2. `feature/기능명` 브랜치에서 기능을 개발한다.
3. 작업 단위에 맞춰 커밋한다.
4. 개발이 완료되면 `develop`을 대상으로 PR을 생성한다.
5. 코드 리뷰 및 테스트를 거친 후 Squash and Merge 방식으로 병합한다.
6. 배포가 필요한 경우 검증된 `develop`의 변경 사항을 `main`에 반영한다.

## 3. Pull Request Convention

### 3.1. PR 생성 규칙

1. 기능 개발이 완료되면 `develop`을 대상으로 PR을 생성한다.
2. PR 제목은 변경 목적을 명확하게 나타내도록 작성한다.
3. PR 본문에는 작업 내용, 주요 변경 사항 및 테스트 결과를 작성한다.
4. 코드 리뷰와 필요한 테스트가 완료된 후 병합한다.
5. 병합 방식은 **Squash and Merge**를 사용한다.
6. 특별한 사유가 없다면 기능 브랜치의 작업 커밋을 하나로 합쳐 병합한다.

### 3.2. PR 제목 형식

`<작업 타입>: <작업 내용>`

- `feat: 회원가입 화면 구현`
- `fix: 로그인 토큰 만료 오류 수정`
- `refactor: 자세 분석 로직 구조 개선`
- `docs: 아키텍처 문서 업데이트`

### 3.3. PR 본문 템플릿

```markdown
## 작업 내용

- 구현하거나 수정한 내용을 작성한다.

## 주요 변경 사항

- 주요 변경 사항을 항목별로 작성한다.

## 테스트

- [ ] 정상 동작 확인
- [ ] 관련 테스트 코드 실행
- [ ] 예외 상황 확인

## 참고 사항

- 리뷰어가 알아야 할 내용이나 관련 이슈를 작성한다.
```

### 3.4. PR 병합 규칙

- **병합 방식:** Squash and Merge
- **대상 브랜치:** `develop`
- **병합 조건:** 코드 리뷰 및 테스트 완료
- **병합 후:** 작업 브랜치를 삭제한다.

Squash and Merge를 사용하면 작업 브랜치의 여러 커밋을 하나의 커밋으로 합쳐 대상 브랜치에 반영할 수 있다. 이를 통해 `develop`의 커밋 이력을 간결하게 유지한다.

---

## 4. 전체 개발 흐름

1. `develop`에서 `feature/기능명` 브랜치를 생성한다.
2. 기능을 개발하고 규칙에 맞게 커밋한다.
3. 작업 완료 후 `develop`을 대상으로 PR을 생성한다.
4. 코드 리뷰 및 테스트를 진행한다.
5. Squash and Merge로 병합한다.
6. 병합된 기능을 통합 및 검증한다.
7. 배포할 버전을 `main`에 반영한다.

## 5. 작업 완료 체크리스트

### Commit

- [ ] 작업 타입이 적절한가?
- [ ] 커밋 메시지가 변경 내용을 명확하게 설명하는가?
- [ ] 서로 무관한 작업이 하나의 커밋에 섞여 있지 않은가?

### Branch

- [ ] 정해진 브랜치 구조를 따르는가?
- [ ] 브랜치명이 소문자와 하이픈 규칙을 따르는가?
- [ ] 기능 개발은 별도의 `feature/기능명` 브랜치에서 진행했는가?

### Pull Request

- [ ] PR 대상 브랜치가 `develop`인가?
- [ ] PR 제목과 본문을 작성했는가?
- [ ] 테스트 및 코드 리뷰를 완료했는가?
- [ ] Squash and Merge 방식으로 병합했는가?
- [ ] 병합 후 작업 브랜치를 삭제했는가?
